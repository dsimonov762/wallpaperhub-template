# 0023. Service repositories: one per language and framework, pinned to a template tag

- Status: Accepted
- Date: 2026-11-26

## Context

The template ([README](../../README.md), [STATUS](../STATUS.md)) is finished: contracts, the service specification, the conformance suite, the local environment, CI, Kubernetes. The services are not. The owner wants to compare how different languages and frameworks solve the same problems, so there will be several implementations, and the first (Java 25, Spring Boot 4.2, Maven) is the first of many.
Putting all of them under `services/<name>/<impl>/` of this repository would make the template grow with every language: each with its own build tool, its own CI jobs, its own Renovate noise and its own release rhythm, in a repository whose job is to stay small and language-agnostic. The build of a real JVM, Go or .NET project also wants to be the root of its own repository (a Maven multi-module build, a Go module, a solution file), with the files that IDEs and tools expect there.
What a service repository still needs from the template is exactly what the template exists to provide: the contracts (an implementation generates DTOs from OpenAPI and gRPC stubs from `proto`, loads the i18n bundles, and checks its schema against `db-schema`), the conformance suite, the Compose infrastructure and the tools around it (`make up`, `make schemas`, `make conformance`, `make host`, `make e2e-system`, `make chaos-run`, `make load-run`).

## Decision

1. **One repository per language and framework, holding all four services**, named `wallpaperhub-<language>-<framework>` (the first is `wallpaperhub-java-spring`). Inside, the layout is the idiom of the language (for Maven: a parent POM, a `platform` module with what the four services share, and one module per service). The services of one repository share a build and a toolchain, which is what a language comparison needs; the repositories do not share code with each other.
2. **The template is consumed at a pinned version.** The service repository has a file `.template-version` that holds a tag of this repository (`v0.1.0`), or a branch name while the template is still moving. `scripts/template.sh sync` (a copy lives in the service repository, because it has to exist before the template is there) clones that tag into `.template/`, which is ignored by Git. Nothing is installed globally and nothing is copied except what item 3 says.
3. **The contracts are vendored.** `contracts/` is copied from the pinned template into the service repository and **committed**, and `scripts/template.sh check` (run by its CI) fails when the copy differs from the tag. The build, the IDE and the Docker build context need the contracts without the template being checked out, and a change to a contract then shows up in the service repository's history as a reviewable diff, which is the same reasoning as for generated files ([0016](0016-generated-files-are-committed-and-checked-for-staleness.md)). The conformance suite, the infrastructure, the seed data and the scripts are **not** copied: they are read from `.template/`.
4. **The template's `make` targets keep their names.** A small `Makefile` in the service repository defines its own targets (build, test, `run`, `template-sync`) and forwards every other target to `make -C .template`, after exporting `ACCOUNT_DIR` (and the other `*_DIR`) as the absolute path of the service repository and `ACCOUNT_DOCKERFILE` as the path of the service's Dockerfile inside it. Environment variables win over `infra/.env`, so no file of the template is edited. The Compose file gains one optional variable per service for that purpose (`ACCOUNT_DOCKERFILE`, default `Dockerfile`), because a Maven multi-module image must be built with the repository root as the context.
5. **The conformance suite is the acceptance test of a service repository, and its CI is its own.** `service.yml` of this repository stays what it is: it builds `services/<name>/<impl>/` of this checkout. A service repository has a workflow that does the same steps against its own checkout and the template at the pinned tag, and ends in a job named `ok` like the template's ([0017](0017-every-check-is-a-make-target-ci-is-the-gate-and-hooks-are-a-shortcut.md), [0022](0022-master-is-protected-by-a-ruleset-and-the-repository.md)). Making `service.yml` callable from another repository (`workflow_call` with a `template_ref` input) is a follow-up once two service repositories show what they have in common.
6. **A change to the template that a service repository must follow is a new tag**, and the service repository moves to it in a pull request of its own (`.template-version`, then `scripts/template.sh sync`, which also refreshes `contracts/`). Renovate can propose that bump later. Until the first tag exists, `.template-version` may name `master`.
7. **The Java repository is the first and sets the pattern; the next ones copy the mechanism** (`scripts/template.sh`, the forwarding `Makefile`, the workflow), not the code.

## Consequences

- The template stays small and language-agnostic, and each language gets a repository whose root is its own project. Several people or AI agents can work on different languages without touching each other.
- A service repository is **not self-contained for running the stack**: `make up` needs the template checked out (`scripts/template.sh sync`, one `git clone` of a tag). It is self-contained for building and testing.
- `contracts/` exists twice (in the template and vendored). The check against the tag makes drift a CI failure, not a surprise; editing the vendored copy by hand is wrong, a contract change is a pull request to the template first, a new tag, then a bump.
- Version skew is explicit and visible: the template version a repository was last verified against is one line in one file. The price is a manual (or Renovate-driven) bump when the template changes.
- The Compose variable `*_DOCKERFILE` and the root-as-context convention are new surface of the template; a repository that keeps the older layout (`services/<name>/<impl>/Dockerfile`) works unchanged.
- Documents in this repository that say `services/<name>/<impl>/` describe the in-repository layout, which stays valid for stubs, mocks and anything small. Work packages S1 to S4 are carried out in a service repository, and their *Lane* is that repository.
- The deployment story (WP-C1) will have to say which repository publishes images; that stays open ([STATUS](../STATUS.md), D-4).

## Alternatives considered

- **All implementations in this repository** (`services/<name>/<impl>/`): one place, one CI, and it is how the README's repository layout was first drawn. Rejected for the growth reasons in the context; kept for small things.
- **A Git submodule of the template**: pins a commit natively, but submodules are awkward in CI, in IDEs and on Windows with WSL, and they check out the whole template into the tree that the IDE indexes. A cloned, ignored folder and a pinned tag give the same pin with plain `git clone`.
- **Copying everything the service needs (contracts, conformance, infrastructure) into the service repository**: the repository would run alone, but would carry a second copy of an infrastructure that changes every few weeks, with no reliable way to see what drifted. Only the contracts are copied, because they are what the build needs and they change slowly.
- **Fetching the contracts at build time** (from the tag, into `target/`): no second copy, but builds need the network and a checked-out template, the IDE cannot see the files, and the Docker build would need an extra build context. Rejected.
- **Publishing the contracts as a package** (a Maven artifact, an npm package): the right answer for a larger organization; a pipeline and a registry for something that a `cp` and a check do for now. D-4 (registry) is not decided.
- **A reusable workflow in this repository that service repositories call**: attractive, deferred (item 5): it should be written when two repositories exist to show what is common, and it cannot be tested from this repository's CI alone.
