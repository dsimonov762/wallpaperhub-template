# Architecture decision records

An ADR is a short note that says **what was decided, why, and what it costs**, written when the decision is made. Code shows what the system does; it cannot show the option that was
rejected or the constraint that was true at the time. Six months later somebody asks "why is the outbox only in account-service?" or "why not TLS between the services?", and the answer is a file
instead of a person's memory.

```
make adr-new T="Use gRPC between catalog and account"     # next number, from template.md, Status: Proposed; fill it in
make adr-new T="Use Kafka Streams for digests" SUPERSEDES=0012   # also marks 0012 as superseded, both ways
make adr-check                                            # form, numbering, links, supersessions, index (CI and a git hook run it)
make adr-index                                            # rewrite the table below
```

## When to write one

When a decision is **expensive to reverse, or surprising to a newcomer, or has a plausible alternative that somebody will propose again**: a data store, a protocol, a trust boundary,
how services are tested, a rule the CI enforces. Not for a choice a linter or a code review settles, and not for a task list. One decision per record, a page or less.

## Life of a record

| Status | Meaning |
|---|---|
| `Proposed` | written, being discussed (a pull request is the place) |
| `Accepted` | decided; the system is built, or will be built, this way |
| `Rejected` | looked at and not taken; kept so that it is not proposed again unannounced |
| `Deprecated` | no longer applies, and nothing replaces it |
| `Superseded` | replaced by a later record, named in `Superseded by` |

An accepted record is **not edited** when the world changes, apart from its status line and the `Superseded by` link: write a new record that says what changed and `SUPERSEDES=` the old one.
The history of why you once did it differently is the part worth keeping. (Fixing a typo or a dead link is fine. Nothing enforces this rule except review: `make adr-check` cannot see what a commit changed.)

`make adr-check` fails on: a file that is not `NNNN-short-title.md`, a number that is repeated or skipped, a title that differs from the file name, a missing or unknown `Status` or a bad `Date`,
a missing or empty *Context*, *Decision* or *Consequences*, a `Supersedes` / `Superseded by` pair that does not agree in both records, a relative link to a file or heading that does not exist,
and an index that is out of date. A record that still holds only the comments of the template fails too, so an empty one cannot be committed by accident. Links to other sites are not followed.

## Format

[`template.md`](template.md): a title with the number, `Status` and `Date`, then *Context*, *Decision*, *Consequences* and, when there were options, *Alternatives considered*. `Supersedes` and `Superseded by`
are added by `make adr-new SUPERSEDES=` and nothing else needs them. Links to code and documents are relative, so the check can tell when a file the record talks about has moved.
Decisions about one service only (`services/<name>/<impl>/`) belong in this folder too, with the service in the title, so that there is one numbered list to read.

## What is verified, what is not

Verified: `make adr-selftest` runs 22 cases on a fixture (every rule above, `make adr-new`, and `SUPERSEDES=` marking both records and refusing a second successor; the anchor function agrees with every link of the
README's table of contents). In a git copy with the hooks installed, real `git commit` calls were stopped for a link to a missing file, a README heading that a record links to, a record left as the template and an index
edited by hand; a commit that touches `docs/` runs the check and passes, a Makefile-only commit skips it; every hook passes on every file, and `make check-contracts` still passes with the new decision log in the README.

Not verified: the new step in GitHub Actions (it runs the same two commands), Windows without WSL (the tool is Python 3 and the targets need `make`, like the rest of the repository), and the content of the first nineteen records against
the intent of whoever decided: they were written from the README and the documents, which is all the repository records of why. Read them, and change a Status to `Proposed` or write a superseding record where they are wrong.
